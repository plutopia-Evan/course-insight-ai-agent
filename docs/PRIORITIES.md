# 产品改进优先级

排序依据：先让使用路径和调用结果可解释、可复用，再证明分析可信，随后降低使用成本，最后优化规模化能力。

| 顺序 | 改动 | 为什么先做 | 验收条件 | 当前状态 |
|---|---|---|---|---|
| P0 | 统一 API 结果与工具调用契约 | 旧文档引导重复分析，用户也容易混淆各入口能力 | 三个上传入口返回统一分析编号；查询/报告复用不新增模型调用；错误状态不丢失 | 本轮已实现，待部署 |
| P1 | 人工标注与独立质量评测 | 自动测试不能证明反馈理解准确 | 金标准、独立检验集、拆分召回、标签 F1、证据支持与失败率可复核 | 待准备真实脱敏数据和标注 |
| P1 | 输入校验与统计口径可见 | 映射错误、漏题和样本过滤会影响结论 | 映射冲突/未知题预览；总人数、有效反馈人数、分类失败与过滤比例清晰展示 | 待实现 |
| P2 | 简化运营操作并统一内部分析服务 | 网页需要两次启动，API 与网页能力尚不相同 | 统一服务支持配置映射与批量课程；前端有清晰步骤、样例和配置复用；各入口结果可核对 | 待实现 |
| P2 | 真正可用的报告建议 | 频率优先级不能代表问题严重性 | 优先级结合样本规模、严重性和整改成本；关键结论有人审 | 待验证 |
| P3 | 成本、耗时和批量处理 | 当前缺少完整调用费用记录，分类以串行为主 | 真实 token、重试、缓存、总时延；任务队列、有限并发、失败重跑 | 待实现 |
| P3 | 多人上线与使用效果 | 本地报告和服务级令牌不足以支持多租户 | 持久化共享存储、账户授权、数据保留；真实任务效率与采用率 | 待实现 |

## 本轮实际变更

- 每次 API 分析保存独立结果，返回 `analysis_id`。
- `GET /analyses/{analysis_id}` 查看已有统计、反馈和报告链接。
- `POST /generate_report` 支持传入 `analysis_id`，复用现有报告；兼容首次上传 `file`。
- 标准分析、Dify 和报告接口共用结果字段，Dify 旧字段保留兼容。
- 修正工具说明中的旧顺序：首次分析已经包含分类和报告，不应把三个全量处理工具连续调用。
- 明确网页/API 的能力差异；未把本轮改动描述成所有入口已统一内部实现。

## 验收与边界

回归测试通过模拟分类器核对：三个上传入口、完整/部分失败结果、重复查询和取报告零新增模型调用、单份报告复用、参数冲突、失效结果和鉴权。真实模型分类质量需要单独评测。

本轮验证：完整自动测试 **56 项通过**（原有 43 项，新增 13 项）；未调用付费模型或改动线上部署。

当前复用依赖用户或外部 Agent 保留 `analysis_id`。重复上传同一文件仍创建新分析，已有版本产生且没有分析记录的报告不能凭空补出编号。结果文件需要和报告一起持久化；尚未部署或修改 GitHub 远端。
